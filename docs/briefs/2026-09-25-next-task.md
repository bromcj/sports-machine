# Next task: turn the machine into a scanner that finds wrong prices, proves them, and can act where it's allowed to

This overwrites the previous `NEXT_TASK.md` (the cleanup brief). Archive that one under `docs/briefs/` first, as before.

## What this is

The machine's job changes. It no longer predicts games. It **finds prices that are wrong, proves it before money moves, and acts only where nobody limits winners.** The forecaster was one way to find wrong prices and it failed three times against real markets. The engine underneath it, fair line, EV after fees, grading, gates, pre-registration, is sound and was verified by an outside review. Everything below points that engine at places where wrong prices exist.

Six things get built, in an order chosen so each one stands on the previous:

| # | What | Why it's in this order |
|---|---|---|
| A | Foundations: venues, price table, polling, per-strategy gates, capital accounting, paper execution | Everything else needs it |
| B | Promo and boost engine in the scoreboard | Most reliable money, least infrastructure |
| C | Kalshi as a venue (and Polymarket as a price source) | The one venue with no limits and a legal API |
| D | Three backtests on free historical data | Decides which strategies get built at all |
| E | Strategies: sharp-line control, Kalshi taker scanner, weather pilot, plus whatever D passed | Each behind its own gates |
| F | Paper period and the go-live protocol | The only path to real money, and it's manual |

**This is a lot. It is deliberately split so each phase is one session's work with a written handoff, and two of the phases (A and C) get a fresh-session review before anything is built on top of them.** Do not try to do it in one sitting. Do not start a phase before the previous one's handoff exists.

## Rules that apply to the whole brief

- **Autonomy as before:** don't stop for approval. Report points are written to `docs/reports/` and you continue. Stop only on the stop conditions below, and write `docs/reports/BLOCKED.md`.
- **No real money moves in this brief.** Every execution path is paper. Real trading requires a manual switch (Phase F) that only the owner flips, and it does not exist yet.
- **Sportsbooks are decision support only.** Never automate placing bets at a sportsbook; it's against their terms. The machine tells the owner what to bet; the owner clicks.
- **Kalshi automation only in paper/demo until Phase F.** Read Kalshi's current API docs and terms before writing a line; if the docs say something in this brief is wrong, the docs win.
- **Legal kill switch.** Kalshi sports contracts are available in NJ under a court ruling that could change. Build a config flag that disables every Kalshi sports path in one place, and a monitor check that alerts if Kalshi's API starts refusing sports markets for this account.
- **Credit cap for this brief: 6,000** The Odds API credits, enforced in code. Kalshi and Polymarket APIs are free. Weather data is free.
- **Pre-registration before every test.** Every backtest and every strategy has its question, its pass rule and what won't be tuned written into `docs/experiments.md` before any result is looked at. A failure is recorded as a failure.
- **Per-strategy gates.** Each strategy gets its own record in `validation.json`: its own 50-plus graded sample, its own 3 SE bar on `info` (or on realized EV after fees where `info` doesn't apply), its own coverage rule, its own placebo. No strategy inherits another's pass. Gate 3 (`armed`) remains a human act and still isn't called anywhere.
- **Stop conditions:** golden test fails and can't be explained; tests or audit red without a logic change; credit cap hit; a Kalshi API call would place a real order outside demo/paper; anything that would delete live data; a phase's fresh-session review returns "not safe to build on."
- **Handoff after every phase** in the two-part format used last time (for the owner, then for the reviewer). Numbers from commands you ran, quoted.
- CLAUDE.md, the golden test, `pytest`, `python -m audit`, one commit per change with evidence, plain English throughout.

## Phase A: Foundations

Nothing in this phase makes money. All of it is what B–F stand on, so it's built first and reviewed before anything is stacked on it.

### A1. Venue abstraction and one price table

Today the machine knows about sportsbooks through The Odds API. It needs to treat every price source the same way.

- A `venues` concept: `sportsbook:<book>`, `kalshi`, `polymarket`, each with a tiny adapter that turns its native format into one schema.
- One `prices` table (append-only, like everything else): `price_id, venue, market_id, side/outcome, price (as a probability), price_native (american / cents / decimal as received), size_available (contracts or dollars at that price, NULL for books), fee_model, captured_at, source_last_update, raw_ref`.
- One `markets` table that maps every venue's identifier to our canonical event: `market_id, venue, venue_market_id, canonical_game_id or canonical_event_id, market_type (h2h/spread/total/prop/futures/binary), line, resolves_at, resolution_source`. Matching to games goes through `feeds` (start time plus names), never date strings. Non-game markets (weather, economics) get a canonical event key of their own.
- **Fee models are first-class.** A book's vig is implicit in its prices (de-vig as now). Kalshi's is explicit: taker fee `0.07 × P × (1 − P)` per contract, maker fee 0 on most markets (read the fee schedule; some series differ). Polymarket's fees per its docs. Every EV in the system is **after fees**, and the fee model used is recorded on the row.
- `fair_value(market_id, at)` becomes one function: Pinnacle no-vig when present, else consensus across books, else the venue's own mid, with the source recorded. Every strategy calls it. Nothing computes fair value on its own.

### A2. Budget-aware polling loop

The twice-a-day scheduled task can't feed a scanner. Build a local polling loop (a long-running process the scheduled task starts and watches) with cadence set by time-to-start:

- more than 24h out: every 60 min; 6–24h: every 15 min; 1–6h: every 5 min; last 90 min: every 1–2 min; in play: stop.
- The Odds API is the only metered source. Show the math: with a named bookmaker list (one region up to ten books) and three markets, budget the month so the whole brief stays under the cap and normal operation on the 20K plan stays under ~15k a month. Kalshi and Polymarket are polled on the same schedule for free.
- Log credits remaining after every metered call; the monitor alerts at 25% and 10% left.

### A3. Capital accounting

Every paper position records: stake, price, fee, days to resolution, and `annualized_ev = ev / days_to_resolution × 365`. Reports show both raw EV and annualized, and total capital locked by strategy and by resolution month. A 5% edge on an eight-month contract must display as what it is.

### A4. Per-strategy gates and the strategy registry

- A `strategies` registry: each strategy has a name, a venue list, a signal function, a paper-execution function, a grading function, a placebo definition, and its gate record. Adding a strategy is a file, not a rewrite.
- `validation.json` gains one block per strategy with the same shape as today's sport blocks. `arm()` takes a strategy name and still refuses unless that strategy's gates 1 and 2 pass. Nothing automated calls it.
- The scoreboard reports per strategy, per venue, and in total.

### A5. Paper execution adapter

- A `paper` ledger that records intended orders (venue, market, side, size, limit price, time), then simulates fills against the *next* observed price and available size, never the current one (no look-ahead). Partial fills are real; record them.
- For Kalshi specifically, if a demo environment exists in the current docs, the adapter can also place orders there. Either way, our own ledger is the record the gates read.
- A hard daily exposure cap per strategy, in config, enforced before any paper order.

### A6. Tests, audit, docs

Unit tests for the price schema, fee models, `fair_value`, the polling cadence, fill simulation (no look-ahead), and annualization. Audit checks that no code path can place a non-paper order. Docs updated (`state-of-the-machine.md`, COMMANDS, the integration matrix script must know the new entry points).

**Report point A.** Then **stop and run a fresh-session review of Phase A only** (a new session, same method as REVIEW_TASK.md but scoped to these commits). Its verdict must be "safe to build on" before Phase B starts. Write the review prompt into the handoff so the owner can start that session.

## Phase B: Promo and boost engine (money first)

The one thing NJ retail bettors make consistent money on is the books' own promotions. Most people take them blind. This is the piece that values them correctly, tells the owner the best bet to attach them to, and grades the result.

### B1. Promo types and their value

Implement as a small library with one function per type, each with unit tests against hand-computed cases. `p` is the fair probability from `fair_value`, `d` the decimal price offered, `S` the stake.

- **Odds boost** (enhanced fixed price): `EV = p × d_boosted − 1` per dollar. Bettable when positive after any max-stake cap.
- **Profit boost** (winnings × (1+b)): `EV = p × (1 + b × (d − 1)) + p × (d − 1) − 1` simplified to `p × (d − 1) × (1 + b) − (1 − p)`. Best attached to the highest fair-probability bet with the largest `(d−1)` the book allows; the engine searches the priced slate for the maximizer.
- **No-sweat / risk-free bet** (lose → bonus bet of stake): `EV = p × (d − 1) − (1 − p) × (1 − v)` where `v` is the bonus-bet value ratio (record the assumption; default 0.70, and estimate it from the owner's own converted bonus bets over time). Best attached to *low* fair-probability, high-payout bets; the engine searches for the maximizer.
- **Bonus bet** (stake not returned): `EV = p × (d − 1) × F` where `F` is face value; convert on longshots at fair-ish prices; the engine finds the best conversion on the slate.
- **Deposit match / playthrough**: value = match × (1 − expected loss over the playthrough at the fair line), with the loss computed from the vig actually paid; report whether it's worth the turnover.
- Boosted parlays and SGP boosts: price each leg at fair, multiply, compare to the boosted payout; flag legs with correlation the book's own pricing already ignores (same-game) as "correlated: value uncertain."

### B2. Entry and recommendation

- Enter a promo in one line or a CSV row: book, type, parameters (boost %, max stake, expiry, eligible markets), and the engine returns the ranked list of eligible bets on today's priced slate with EV, recommended stake, and the fair line used.
- Every recommendation is logged with the snapshot it used. If the owner takes it, they enter the bet with tag `promo:<type>`; it's graded like everything else (`ev_fair_close`, `shop`, `info`, closing window, coverage), plus `ev_at_entry` for the promo math.

### B3. Reporting and gates

- Scoreboard section: promos by book and type: n, EV at entry, realized ROI with CI, bonus-bet conversion rate observed (feeds `v`).
- Gate record `promo`: 50-plus graded, realized EV after fees clear of zero by 3 SE. Placebo: the same promos attached to a random eligible bet instead of the maximizer; the engine must beat its own placebo.

**Report point B**, with a demo on three fake promos, then deleted.

## Phase D: Three backtests on free historical data

All pre-registered before any data is pulled. All on Kalshi's historical endpoints and Polymarket's public data, which cost nothing. Each answers one question with one pass rule, and each includes the same day-block or market-block bootstrap for its CI.

### D1. Consistency violations

Across Kalshi, Polymarket and (where our archive has them) sportsbook futures: how often do related prices contradict each other, by how much, and how long do the gaps last? Define the relations precisely before looking: exclusive outcomes summing over 100% after fees; nested events (A ⊂ B priced with P(A) > P(B)); date ladders; the same event across venues differing by more than fees plus spread. Measure frequency per day, median size, median lifetime, and depth at the time. **Pass:** a repeatable class of violation exists with median size above fees plus spread and median lifetime above two polling intervals.

### D2. Longshot selling

On settled Kalshi markets: what did selling contracts priced under 10¢ (and under 5¢, and under 20¢) return by category and by days-to-resolution, after taker fees, including every loss? Report the return distribution, the worst month, the max drawdown, and the annualized return net of capital lockup. **Pass:** positive annualized return after fees in every category tested, with the worst-case tail inside a limit the owner would tolerate (state the limit in the pre-registration).

### D3. Cross-venue divergence

Where Kalshi and Polymarket price the same event more than X apart, which one was right at settlement, and did the gap close before resolution? By category and horizon. **Pass:** one venue is systematically better in a category by more than fees, clear of zero by 2 SE, and the gap is capturable (depth existed at the time).

Record every verdict in `docs/experiments.md`. Strategies E4 and E5 exist only if D1 and D2 pass.

**Report point D.**

## Phase E: Strategies, each as a registry plugin behind its own gates

Build in this order. Each one is paper-only through A5.

### E1. Sharp-line control on sportsbooks (item 6)

For every game and market with a Pinnacle price: flag any NJ book beating the fair line by more than 1.5% EV after vig. Log as strategy `shop`, decision support only (owner clicks), graded like everything else. Purpose stated in the docstring: it's +EV by construction, so a negative result means the fair-line or grading code is broken; and it answers whether "nothing to shop" was under-observed with four books. Report flags per hundred games after two weeks.

### E2. Kalshi taker scanner (item 4)

Every poll: compare Kalshi's best ask (for yes) and best bid (for no) against `fair_value` from Pinnacle. When the after-fee EV of *taking* the resting quote exceeds a threshold (start at 2%), place a paper taker order for the smaller of the available size and the exposure cap. Never post resting orders on sports in this brief; the professional makers have faster feeds and will pick off stale quotes. Grade against the fair close and settlement. Placebo: take a random quote at the same times. Report: opportunities per day, fill rate against next-observed book, EV after fees, `info`.

### E3. Weather pilot (item 5)

Kalshi's daily high-temperature markets for the cities it lists. Fair value from a forecast distribution built from the National Weather Service (free API) and, if accessible, the National Blend of Models percentiles, calibrated on the past year of NWS forecasts vs official station readings for each city (settlement uses the official station; identify it per market). Pre-register the calibration method. Paper-trade as a **taker** when the after-fee EV exceeds threshold and as a **maker** (resting order at fair minus edge) where the book is thin, because on weather the counterparty is retail, not a sharper maker. Placebo: a climatology-only forecast. This is the one place a forecast model of ours competes with a retail crowd; report it that way.

### E4. Consistency arbitrage (only if D1 passed)

Detect the violation classes D1 found, size the position to the smaller leg's depth, paper-execute both legs, account for capital lockup, and grade to settlement.

### E5. Longshot selling (only if D2 passed)

Sell (buy "no" on) contracts in the categories and horizons D2 passed, with position limits per market and per resolution month, paper-only, graded to settlement with the tail tracked.

Each strategy: pre-registration, gate record, placebo, scoreboard section, tests, docs, integration-matrix entry.

**Report point E.**

## Phase F: The paper period and the go-live protocol

- Run every strategy in paper for **four weeks minimum**, or until its gate 2 sample is met, whichever is later.
- Weekly: `python -m sports_machine scoreboard` with per-strategy verdicts, plus a one-paragraph plain-English note in `docs/reports/weekly-<date>.md` on what passed, what failed, what's undecided.
- **Go-live protocol, written now, executed later by the owner:** a strategy goes live only when gates 1 and 2 pass, the placebo fails, a fresh-session review of that strategy's code says "safe," and the owner personally calls `arm("<strategy>")`. Live is Kalshi only, maker-preferred where the venue allows, with a daily exposure cap and a drawdown stop (pause at −15% from peak) in config. Sportsbook strategies never go live in software; they stay decision support.
- The protocol is a document plus the config flags; **the production order path is not built in this brief.**

## Sports coverage: more markets, no more models

The scanner's edge scales with how many priced markets it watches, not with how well it forecasts. So **NFL, NBA and NHL are all in scope as price coverage** (sportsbooks, Kalshi, Polymarket) for E1, E2, E4 and E5, within the credit budget in A2: NFL now, NBA and NHL from their opening nights. MLB rejoins in March. **None of them gets a forecasting model.** The NFL sides model stays as a research artifact; it lost to the market by 0.037 and is not rounded out, and no NBA or NHL model is built. The reason is the same three times over: public-data forecasters lose to main markets, and the scanner doesn't need one.

## Not in scope

Any game-outcome forecasting. Rounding out the NFL model. NBA or NHL models. Buying historical sportsbook data. Any real order. Anything that weakens a gate.

## The size of this

Phases A and C are the foundations and get reviews. B is the money. D is research. E is five plugins on one interface. F is a document and a schedule. Sequence matters more than speed: a strategy built on a price table that's wrong is worse than no strategy, and the last review showed exactly how that happens.
